# M1.5 Python worker

Godot 4.7.1 was verified on Windows with Python 3.11.5. The worker uses only the Python standard library.

1. In PowerShell, run `python --version` and `Get-Command python.exe` to check that a local Python installation is available. PyWars searches `PATH` for `python.exe`. To use a specific interpreter, set `PYWARS_PYTHON` to its absolute executable path before launching Godot. In a new PowerShell session, for example:

   ```powershell
   $env:PYWARS_PYTHON = 'C:\path\to\python.exe'
   & 'C:\path\to\Godot.exe' --editor --path 'D:\code\PyWars'
   ```

2. Open PyWars in Godot and press **F5**. The HUD shows the connection, active behavior file, current action, tick, carried Ore, and HQ Ore. The full error and any Python output are in Godot's output log.
3. Stop the game, edit `python/worker.py`, save, and press **F5** again. The runner loads the file at startup. To see the effect of a different policy, replace `on_tick` with the following function. The worker stays at spawn, and HQ Ore stays at zero.

   ```python
   def on_tick(observation):
       return {"kind": "idle"}
   ```

## Worker API

`on_tick(observation)` returns one action dictionary. Positions are two-element lists of integer grid coordinates `[x, y]`. Grid `y` corresponds to scene `z`.

| Observation key | Value |
| --- | --- |
| `tick_id`, `robot_id` | The upcoming tick number, starting at `1`, and the robot's string identifier (`worker_0`). |
| `position`, `hq_position` | The worker's cell and the friendly HQ's cell. |
| `walkable_neighbors` | The currently free cardinal neighbors in stable right, up, left, down order. |
| `ore_deposits` | Visible deposit entries with `id`, `position`, and `remaining`. This arena exposes only the friendly deposit (`ore_0`), including when it is depleted. |
| `carried_ore`, `capacity` | Ore currently carried and the maximum carried (3). |
| `last_action` | Previous resolution: `idle`, `moving`, `mining`, `depositing`, or `rejected`. |
| `mining_ticks`, `mining_ticks_required` | Progress toward the next unit of Ore and the ticks required (3). |

| Action returned | What Godot validates and applies |
| --- | --- |
| `{"kind": "move_to", "target": [4, 4]}` | Move one cell to a free cardinal neighbor. For longer travel, the policy chooses one neighbor toward its destination each tick. |
| `{"kind": "mine", "deposit_id": "ore_0"}` | Count one mining tick if the deposit is valid, adjacent and nonempty, and the worker has space. Repeat on consecutive ticks to collect Ore. |
| `{"kind": "deposit"}` | Transfer all carried Ore into the friendly HQ when the worker is adjacent to it. |
| `{"kind": "idle"}` | Take no new action. As in M1, a tick without valid mining clears partial mining progress. |

## Runner and tick timing

The arena starts one local Python subprocess via `OS.execute_with_pipe` with nonblocking pipes. Godot sends each `observe` JSON line with `tick_id`, `robot_id`, and `observation`. Python replies with a `decision` line carrying both IDs and `action`, or an `error` line carrying both IDs and `message`. A `ready` or `startup_error` message reports startup. Behavior prints and tracebacks use stderr. Godot polls the pipes on the main thread without waiting for replies, then resolves actions through the M1 simulation at tick boundaries.

The runner has one outstanding request at a time. After startup completes or fails, the arena advances every 300 ms while running normally. Each observation is sent for the next tick. If its reply is missing at the boundary, the worker idles for that tick. A late reply is discarded, and the bridge can then request a decision for the next tick. Duplicate or mismatched replies cannot supply an action. The arena's `python_timeout_ms` Inspector setting defaults to 2,000 ms for startup and for each outstanding decision. A timeout terminates the runner. A process exit or startup failure also leaves the worker idle. Restart the prototype to retry. A handled exception inside `on_tick` leaves the runner available for later ticks.

Headless tests drive the same arena and wait for matching replies before stepping when verifying successful decisions. Real-time missed deadlines can change live outcomes. The tests also use the live timer to verify that simulation ticks continue during a stall and after the runner exits.

## Headless verification

From the project folder, substitute the path to the installed Godot console executable:

```powershell
$godot = 'C:\path\to\Godot_console.exe'
& $godot --headless --path . --max-fps 90 --script res://tests/m15_python_test.gd
& $godot --headless --path . --script res://tests/m1_simulation_test.gd
```

The M1.5 suite intentionally prints Python diagnostics while testing failure cases. The final pass line and exit code indicate the result.

## Development security boundary

Run trusted local behavior files only. The Python subprocess runs with the developer's OS permissions and can use the filesystem, network, and process APIs available to that account. JSON validation protects the simulation's action interface. It does not restrict what Python itself can do. Player-submitted code will require OS-enforced isolation, explicit filesystem, network and process restrictions, resource limits, and tests of those boundaries. This prototype exercises one robot and one behavior. The protocol carries robot and tick IDs so later work can route decisions through a shared runner without launching one process per robot.
